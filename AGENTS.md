# Agent guide

This file is the entry point for agents working on Dama Pinoy. Read [README.md](README.md) for setup, gameplay, and dependencies, and [CHANGELOG.md](CHANGELOG.md) for release history. There is no separate formal product specification in this repository.

## Project map and conventions

- `index.html`: eight accessible screens and settings/controls, including Account. Use semantic markup, labeled inputs, keyboard-accessible buttons, and the existing DOM IDs.
- `style.css`: wood-first board-game design with Night and Light themes, consistent spacing/surfaces, visible focus, reduced-motion support, and responsive layouts. Keep the title usable at short desktop heights and prevent horizontal overflow on mobile.
- `script.js`: self-contained Dama rules, AI, series, replay, and browser storage. Keep the current test hook under `__DAMA_TEST__` and reuse it for behavioral checks. Red moves first in every game as this app's convention; Player 1/the human chooses a Game 1 color and players swap colors each series game. Player 1's pieces appear at the bottom: visually reverse board squares and coordinate labels when Player 1 is Blue, without changing logical row/column, notation, or rules. Keyboard board navigation follows visual directions; new replays retain the game's view and replay version 1 uses the original Red-bottom view. Player IDs (`P1`, `P2`) own names and scores; board colors (`R`, `B`) own pieces and moves. Existing `R`/`B` names and scores migrate to `P1`/`P2`; saved replay version 1 remains readable. The AI must play whichever color belongs to `P2`. `MATCH_GAME_LIMITS` defines valid formats and their game limits; the series ends on a majority of wins or at that limit. At the limit, the higher score wins or a tie draws the match. Draws consume a game but award no series point. An ordinary piece that reaches the far row during a capture chain keeps jumping as an ordinary piece and promotes only when that turn ends there.
- `manifest.json`, `service-worker.js`, `icons/`: local PWA assets. Increment the versioned service-worker cache name when changing cached app files, so installed clients receive updates. Register only on localhost or HTTPS.
- Statistics are stored under `damaPinoyStatsV1` and are separate from the all-time win counters. Record only completed games and finalized matches; restarts, abandoned games, and replay viewing must not record. Local two-player results use Player 1's perspective; vs Computer results use the human player's perspective. AI mode keys are `vsEasy`, `vsMedium`, and `vsHard`; drawn series count as played but not won or lost. Reset Statistics must preserve names, preferences, the saved replay, the active game, and the all-time win counters.
- Replay downloads use a separate JSON file format (`format: "dama-pinoy-replay"`, `version: 1`) with `P1`/`P2` ownership, ordered captures, and an explicit Red- or Blue-bottom view. The internal stored replay versions 1 and 2 remain readable. Export the open replay from the viewer or the saved replay from Game Over. Import validates metadata and board sequence before opening the read-only viewer; it remains in memory and must not replace Last Replay or change the game, statistics, scores, names, or preferences. Use visible non-blocking status text; file transfer must work offline and over `file://`.
- Online Single Game and Best of 3/5/9 series live in `online.js`/`online-rules.js`, separate from local game state and statistics. The host chooses the fixed room format and Game 1 color; colors swap each game, Red always opens, scores follow users, draws consume a game, and both users confirm the next game or new series. `online-rules.js` is also imported by the Supabase Edge Function; keep it in parity with the local Dama rules. A verified anonymous Supabase Auth user ID owns each room seat; the guest ID in localStorage is informational, never authorization. Private Broadcast/Presence messages are hints only: fetch and validate the database snapshot before rendering. Edge Function checks full moves; service-role-only SQL RPCs commit them atomically. Only the local mover may render a locally validated optimistic move, and rejection must restore and fetch the authoritative snapshot. No online result changes local scores, statistics, names, or Last Replay. Online scripts are local/cached, but the Supabase CDN client is loaded only on entering online mode; local offline and `file://` play must remain functional.
- `supabase/migrations/20261024_online_single.sql` defines the base tables, RLS, and private Realtime policies; `supabase/migrations/20261025_online_match_options.sql` adds online series/per-game colors and replaces the privileged RPCs. `supabase/functions/online-room/index.ts` holds guest authentication, validation, and room actions. Service-role credentials belong only in Edge Function environment variables. `online-config.js` contains the public project URL and publishable key; update the service-worker cache version when editing it. The remote GitHub `main` may lag this workspace; review remote changes before any sync, and do not push without explicit permission.

## Checks before completion

### v2.3 accounts

- `supabase/migrations/20261027_player_accounts.sql` adds private profiles and service-recorded online account game/series statistics. Existing room/replay ownership already uses Auth UUIDs for anonymous and permanent users; do not add redundant identity columns or weaken required seat ownership. Profile creation runs on Auth insert/anonymous upgrade; profile reads/edits and statistics reads are owner-only via RLS. Statistics writes are server-only triggers, unique per game/series/user.
- Account UI/session code remains in `online.js`. Anonymous signup uses `updateUser` to retain the seat's UUID. Different-account login, logout, and new-guest switching require leaving saved/current rooms first. Same-account password reauthentication checks the identity in a non-persisted SDK client before replacing the main session, preserving the seat. Auth generations and captured-session requests reject stale profile/results after logout; clear private replay metadata/viewer buffers on identity changes. Profile changes affect new room names, not historical snapshots. Show Guest/Account labels without exposing email to opponents. Account Statistics replace the dashboard view while logged in; local/AI records are never merged/uploaded and return after logout.
- Deletion requires `DELETE`, a verified permanent Auth identity, and login within 15 minutes. The Auth deletion trigger closes rooms and replaces the deleted UUID/name in shared records with a random tombstone/Deleted player, while FK cascades delete profile/private stats. Preserve opponents' replays and local browser data. Never log credentials or hard-code service-role keys.
- Auth uses the existing CDN SDK, PKCE, persisted sessions, and same-browser email callbacks; restore on app load only if a Supabase session/callback exists. Auth is HTTPS-only except localhost; local offline and file play must stay independent. Do not cache query-bearing callbacks or authenticated/API responses. Email delivery/redirect/provider configuration needs operator setup; mark real email round trips NOT RUN without working sender/inbox access.
- Process captured email callback codes exactly once with `exchangeCodeForSession`; keep SDK `detectSessionInUrl: false` and `flowType: "pkce"`. Do not fall back to implicit bearer-token URL sessions. Gate background Auth sync while exchanging, verify the returned account/upgrade UUID, strip callback credentials from history before loading the CDN, and keep callback failures visible. The pinned Auth SDK's automatic PKCE path drops the recovery marker and ignores code-only callbacks without a verifier; do not rely on it. Recovery UI state in sessionStorage contains only a user ID/time, never tokens, and must be cleared on password update/logout. Use disposable real GoTrue verify/PKCE fixtures in addition to mocked UI checks; fixture verification is not proof of actual SMTP/inbox delivery.
- v2.4 password reset uses typed email OTPs (`verifyOtp` with `type: "recovery"`), separate from signup/magic PKCE callbacks. Request/verification clients are non-persisted and must not overwrite the main PKCE verifier. Verify the returned user/email before installing the recovery session and gate background sync during installation. Both requesting and verifying require leaving saved/current rooms; reject stale identity changes. Never persist/log codes or reset email input. The Reset Password email template must show `{{ .Token }}` only; retain confirmation URLs for signup/magic templates and compatibility with existing recovery links. Include cross-browser/no-verifier recovery, expired/wrong/reused codes, resend cooldown/server limits, password update, refresh, room guards, and data isolation in verification.
- v2.4.1 account access is a focused email/password Log In form with Create Account and Forgot Password entry points, not a tabbed list of Auth methods. Signup always requires a password and preserves the guest UUID. Do not reintroduce magic-link request/passwordless-signup controls, duplicate guest navigation, or an "already have code" branch. Keep previously issued callbacks readable. Show resend only at the OTP step, contextual headings, Back to Log In for signup/reset, and the existing menu/online return for guest play. Existing passwordless accounts can use OTP recovery to set a password.
- Verify signup/upgrade, email/password login, magic/recovery callback UI, profile RLS, cross-device stats/replay ownership, logout isolation, deletion anonymization, expired sessions, spectator/series/rejoin compatibility, and desktop/mobile account layouts. README documents the approved online-only stats and deletion policies and Auth deployment settings.

### v2.2 online additions

- `supabase/migrations/20261026_online_replays_spectators.sql` adds `online_replays` and `room_spectators`. Replay recording is an `AFTER UPDATE` game trigger within the move transaction, unique by game ID. Do not save online records through local `saveLastReplay` or statistics paths. `DamaPinoyApp.openOnlineReplay` validates and opens in-memory replay-file data; online JSON exports retain file version 1 with mode `online`.
- Replay ownership maps host to `P1`, guest to `P2`; save `series_number`, actual game colors, and both player orientations. Players retain replay access through their original verified Auth IDs until retention cleanup. Active, unexpired room spectators can read room replays only while the room is active/finished. No public replay reads or client writes are allowed.
- Spectator membership is Auth-owned, limited atomically to five under the room row lock, and expires after 60 seconds without heartbeat. Spectators receive private hints and may send Presence only, never authoritative moves/rematch requests. Spectator heartbeat never extends player grace or room inactivity. Spectator leave removes only membership. The spectator board is Red-bottom.
- Reuse `rooms.version`; do not add a second version counter. Rejoin requires confirmation and a freshly verified snapshot. Epoch/room guards reject in-flight state after leaving. Local saved IDs are hints, not authorization. Check three browsers (two players and a spectator), six-spectator rejection, direct API/RLS denials, replay recording/export/import/ownership, rejoin within and beyond grace, stale sync races, and all existing regressions.

Run `node --check script.js`, `node --check online-rules.js`, `node --check online.js`, and `node --check service-worker.js`. Check color selection/persistence, local series/draws/orientation, AI, replay export/import, statistics isolation, offline local play, and desktop/mobile layouts. For online, compare the pure rules against the local test hook, then check host color/format selection, room creation/join, private presence, Red opening and color swaps, series scoring/draw limits, next-game/new-series confirmation, optimistic rollback, moves and turn locking, maximum capture chains, promotion, stale/invalid move rejection, disconnect/reconnect, leave, and database resynchronization in two browsers against a live Supabase project. Mark live checks NOT RUN until a project URL and publishable key exist. Confirm only intended files changed; update the changelog with each feature or fix.

**Requirements note:** This agent guide is not intended as a full ISO/IEC/IEEE 29148 requirements specification. It applies clear, testable implementation constraints but simplifies formal requirement IDs, rationales, priorities, acceptance criteria, and traceability; the player-facing behavior is documented in README and the in-app How to Play screen.
